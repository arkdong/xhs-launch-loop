# 反馈解读（阶段 ③ 与 ④）

脚本负责解析和计数，这里说明怎么把计数变成判断，以及脚本数不准时怎么办。

## 1. 评论怎么进来

`comment_insight.py` 自动识别下面几种输入，不需要用户整理：

| 输入 | 说明 |
|---|---|
| 评论区直接复制 | 用户名、评论、时间属地、赞、回复各占一行。用户名、时间、点赞数、「回复」「展开」这些行不会被当成评论 |
| 每行一条评论 | 也认「昵称：评论」和 Markdown 表格 |
| csv、tsv | 需要有 评论 / 内容 / content 列 |
| json | 字符串数组，或带 content 字段的对象；笔记数据里嵌套的评论列表也能找出来 |

- UTF-8 和 GBK 都能读；文件名写 `-` 表示从标准输入读；可以一次给多个文件。
- **作者回复不算用户反馈。** 带「作者」标记的评论会单独分出来；复制的内容里没有这个标记时，用 `--author "作者昵称"` 指出来。
- 引流自荐、互关、给平台助手下指令这类和产品无关的评论会被过滤，并在报告里单独计数。同一个人的同一句只算一次。
- **核对条数。** 报告第一行写着「读到 N 条，其中有效评论 M 条」。和原文对一下：条数对不上，或者有 ⚠️，说明解析可能有误。确认条数无误后加 `--checked` 重跑；确实不对就把评论整理成每行一条再跑。解析有疑点且没核对时，这批评论不能用来给假设下结论。
- 想看每一条被归成了什么，加 `--detail`。

保存位置：`--research` 存为调研用的洞察，`--id L2` 存为发布 L2 的反馈，之后的 `analyze` 和 `verdict` 会自动读取。

## 2. 评论报告怎么读

| 部分 | 怎么读 |
|---|---|
| 意图分布 | 一条评论可以同时属于几种意图。购买意向和提问多，说明购买方式、价格这些信息没给够 |
| 关注点 | 每个维度分吐槽、疑问、好评三栏。**吐槽满 3 条才算「痛点」**；疑问满 3 条是「信息没给够」；其余都是「线索」 |
| 问题主题 | 按主题计数的提问，可以直接当选题。「待回复」交给用户，提醒 24 小时内回复 |
| 用户建议 | 「希望出小包装」这类原话，进产品改进清单 |
| 作者回复 | 回复里的说法要和笔记正文、卖点一致（例如续航时间、价格），不一致要指出来 |
| 词表覆盖 | 没有归入任何意图或维度的评论占比。超过四分之一时，多半是品类特有的说法没被认出来，按第 5 节补词表 |

评论分两类去向：

| 类型 | 判断 | 去向 |
|---|---|---|
| 产品反馈 | 说的是产品本身：太苦、太贵、包装漏、想要小包装 | 产品改进清单 |
| 内容反馈 | 说的是笔记：没看懂、求教程、像广告、想看对比 | 下一次发布简报 |

同一条评论可以两类都算。有效评论不到 20 条时，整份报告只能当线索。

## 3. 数据怎么读

| 指标 | 算法 | 反映什么 | 低了改什么 |
|---|---|---|---|
| 点击率 | 观看 ÷ 曝光 | 封面和标题 | 只换封面文字和标题 |
| 互动率 | （赞 + 藏 + 评 + 转）÷ 观看 | 内容是否兑现了标题的承诺 | 正文前两行、具体程度 |
| 收藏点赞比 | 收藏 ÷ 点赞 | 实用价值 | 补步骤、清单 |
| 评论率 | 评论 ÷ 观看 | 有没有讨论的由头 | 结尾提问 |

- 数字有几个填几个，缺的按未知处理。没有观看数时算不出点击率、互动率和评论率，脚本会说明。
- 脚本里的高低阈值是经验值，只用来给方向。**真正的基准是自己的另一篇笔记**，脚本会自动对比并标出主指标。
- 建议在发布后 24 小时、72 小时、7 天各记录一次（`--label 24h`），结论以最后一次为准。

## 4. 对假设下结论

- **成立**：主指标明显好于对照，并且评论内容能解释原因。
- **不成立**：主指标没有改善或更差。这同样是有价值的结果，记下来避免重复。
- **证据不足**：样本太少、没有对照，或同时改了几个变量。

「成立」和「不成立」要过门槛，脚本会检查，没过就拒绝登记并说明差什么：

| 发布目标 | 主指标 | 门槛 |
|---|---|---|
| 所有目标 | | 曝光满 1000；有另一篇有数据的发布可以对比；主指标在两篇上都算得出来 |
| 互动，或没定目标 | 评论率 | 有效评论满 20 条（以评论洞察的有效条数为准，没有洞察时用录入的评论数）；评论解析的疑点已核对 |
| 收藏 | 收藏点赞比 | 点赞满 20 个 |
| 触达 | 点击率与观看 | 不要求评论数 |

- 第一篇没有对照：登记「证据不足」，或者把以前发过的笔记用 `launch_log.py add --baseline` 补登记并录入数据，就有对照了。
- 基线笔记没有假设，复盘时用 `--result 基线`，在 `--learning` 里写它的数据水平。
- `--force "理由"` 只在用户有脚本看不到的依据时用（例如私信里的大量反馈）。理由会写进日志，报告里会标明「证据未达标，强制登记」。

`--learning` 写成下一次可以直接照做的一句话，例如「痛点开头的评论率 1.7%，是基线 0.7% 的两倍多，以后默认用痛点开头」。

## 5. 项目词表：补上品类特有的说法

通用词表覆盖多数消费品、数码、App 和服务，但每个品类都有自己的说法。报告的「词表覆盖」一节提示有漏判，或者你读评论时发现明显的痛点没被数到，就在数据目录里建 `xhs_launch/lexicon.json`（自动加载，不用改技能自带的词表），然后重跑：

```json
{
  "aspects": {
    "质地与手感": {"neg": ["黏键盘", "糊手"], "pos": ["不黏键盘"], "topic": ["成膜"]},
    "燃烧表现": {"neg": ["隧道", "挂壁", "炸芯"], "pos": ["烧得均匀"], "topic": ["烛芯", "燃烧时间"]}
  },
  "intents": {"购买意向": ["求团购"]},
  "spam": ["同款代购"],
  "positive": ["封神"],
  "negative": ["智商税"],
  "mask": ["土耳其"],
  "remove": ["土"]
}
```

| 字段 | 含义 |
|---|---|
| `aspects.维度.neg` | 出现就算吐槽的词（前面有否定词时算好评）。维度名可以用已有的，也可以新建 |
| `aspects.维度.pos` | 出现就算好评的词（前面有否定词时算吐槽） |
| `aspects.维度.topic` | 话题词，和疑问、好评词、吐槽词搭配时才有态度 |
| `aspects.维度.good` | 中性的功能词：「很保湿」算好评，「不保湿」算吐槽 |
| `aspects.维度.adj` / `too` | 单字形容词：`adj` 是贬义的（油、黏），`too` 是过量才算吐槽的（甜、大） |
| `intents` | 给某种意图加词 |
| `spam` | 出现就过滤的词 |
| `positive` / `negative` | 不属于具体维度的通用好评词、吐槽词 |
| `mask` | 含有敏感字但意思无关的词（品牌名、地名），匹配前先遮住 |
| `remove` | 通用词表里在这个品类会误判的词 |

临时试一份词表用 `--lexicon 文件.json`。补了词表还是数不准的少量评论，由你人工清点，在结论里标明「人工计数」并附原话，不要改写脚本的数字。

## 6. 给用户的两份清单

`launch_log.py next` 汇总全部发布。跨发布累计吐槽满 3 条才算痛点，不到的只是线索，不要据此改产品或定下一篇的角度。

**下一次发布简报**：沿用什么（已验证）、放弃什么（已证伪）、新假设是什么、建议的角度和形式。一次只改一个变量。

**产品改进清单**：

| 优先级 | 改进点 | 提及次数 | 用户原话 | 来自哪次发布 |
|---|---|---|---|---|

按提及次数排序。只有一个人提的不进前三，除非是质量或安全问题。
